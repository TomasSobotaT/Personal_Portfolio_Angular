Komponenty a služby SQL Serveru

  • Replikace – automatické kopírování a synchronizace dat z jedné databáze do druhé. Tady pozor, bývá to citlivé a ne vždy spolehlivé.
  • Full-textové vyhledávání – indexační a vyhledávací mechanismus pro texty, který jde mimo klasické LIKE '%text%'. Instaluje se zvlášť.
  • PolyBase – umožňuje dotazovat se na externí data, jako by to byly normální SQL tabulky, bez nutnosti je importovat do databáze.
  • Parquet – sloupcový formát vhodný pro rychlou analytiku nad velkými daty.
  • Machine Learning Services – umožňují spouštět R nebo Python přímo uvnitř SQL Serveru.
  • SSIS – Integration Services – ETL nástroj pro tahání dat mezi DB, soubory a systémy.
  • Master Data Services (MDS) – centrální číselníky a „zdroj pravdy“, dnes už obsolete.
  • Data Quality Services (DQS) – čištění a sjednocování dat, dnes také v podstatě mrtvé / obsolete.
  • SSAS – Analysis Services – analytický server nad daty. Ne databáze, ale „mozková vrstva“ pro rychlé agregace.
  • SSRS – Reporting Services – server na generování hotových reportů, PDF, tiskových výstupů a tabulek.

Tip: některé komponenty má smysl nainstalovat a nechat vypnuté, dokud nejsou potřeba.

Instance SQL Serveru

  • na jednom PC nebo VM může být více instancí SQL Serveru
  • server má default collation, databáze může mít jinou
  • nejlepší je držet collation pokud možno stejně
  • SQL Server typicky využívá sudý počet procesorů rozumněji při paralelismu

Edice MSSQL Serveru

  • Enterprise – nejlepší algoritmy, locking, paralelismus, více funkcí
  • Standard
  • BI – dříve existovala, zanikla
  • Web – speciální licenční scénáře
  • Express – pokusy, učení, malé aplikace; omezené, max 10 GB na databázi, žádný SQL Agent
  • Developer – v podstatě Enterprise bez produkčního nasazení

Jen Express a Developer běžně jdou na desktop OS, ostatní spíš na server OS.

Nasazení v Azure

  • Azure SQL Database – levné, jednoduché, ale ne 100% kompatibilní s on-prem
  • SQL Managed Instance – dražší, ale skoro jako on-prem
  • VM – plná kontrola, dělám si co chci

Přehled architektury

SQL je deklarativní jazyk – říkám co, ale ne jak.

  • Query Execution – SQL Server dostane dotaz, parsuje ho, optimalizuje a vytvoří execution plan
  • Storage Engine – „ruce SQL Serveru“, vykonává plán, řeší zamykání a transakce
  • SQL OS – malý interní OS, který komunikuje s operačním systémem, řeší paměť, CPU, disk a třeba i deadlock monitor

In-Memory OLTP

Vybrané tabulky drží celé v RAM. Dotazy nad nimi běží bez klasických locků a latchů. Na disk se zapisují přes log a checkpointy.

  • týká se jen tabulek, které jsou explicitně MEMORY_OPTIMIZED
  • hodí se pro hodně současných INSERT a UPDATE
  • pro situace s velkým paralelním přístupem na stejná data
  • normální OLTP často stačí dobře cachované v buffer poolu, nemusí být In-Memory

SSMS a konfigurace serveru

SSMS + SQL Server Configuration Manager

Na serveru v context menu

  • Activity Monitor – sledování zátěže, waits, resource usage, paralelismu a dalších věcí

Server properties

  • General – verze, collation
  • Memory – minimum a maximum memory pro SQL Server
  • Processors – procesory pro danou instanci
  • Connections – radši zbytečně nesahat
  • Database settings – cesty k DB, komprese backupu, checksum
  • Advanced – nastavení paralelismu a další low-level věci

Memory

  • Minimum – když SQL dosáhne minima, už pod něj často neklesne
  • Maximum – nastavit rozumný strop, aby zbylo místo pro OS a další procesy
  • tohle nastavení se týká hlavně Buffer Poolu
  • Index creation memory – nechat 0, tedy dynamic
  • Min memory per query – minimální paměť na dotaz; někdy má smysl zvednout tam, kde běží jen velké dotazy

Advanced – paralelismus

  • Cost Threshold for Parallelism – „cena“, od které se execution plan pustí paralelně
  • často dává smysl nastavit třeba 50 místo historického defaultu 5
  • Max Degree of Parallelism (MAXDOP) – kolik procesorů smí paralelní plán použít

Na DB v context menu → Properties

  • Query Store – zapnout uchovávání dotazů a plánů
  • Options → Max DOP – omezení paralelismu na úrovni DB

Instalace SQL Serveru

  • mount ISO
  • SQL Installation Center
  • licence / eval / klíč

Server Configuration

  • Service accounts – nastavit účty pro Engine a Agent
  • Grant Perform Volume Maintenance Tasks – zapnout, pokud nemusím řešit extra security; pomáhá při růstu souborů DB
  • Collation – dobře promyslet hned na začátku

Collation

  • pro nové aplikace často Czech_CI_AS
  • pro staré aplikace někdy SQL_CZECH_CP1250_CI_AS nebo jiné starší varianty
  • accent-sensitive znamená, že třeba Ř a R není totéž

Database Engine Configuration

  • Mixed mode nebo Windows mode
  • přidat current user jako admina
  • Data directories – rozumně rozdělit data, logy a tempdb
  • TempDB – změnit defaultní umístění a počet souborů
  • MAXDOP – nastavit při instalaci
  • Memory – nastavit mantinely
  • FILESTREAM – nezapínat, dokud není potřeba

TempDB

  • často se dává na vlastní rychlý disk
  • počet souborů typicky podle CPU, ale rozumně, ne přehnaně
  • rozumný initial size a autogrowth jsou důležité

Obecně

  • počítat orientačně zhruba 7–8 GB RAM na procesor jako hrubý odhad
  • když je Memory-Optimized OLTP, paměť klidně krát 2
  • odhadem přidat rezervu kolem 20 % velikosti dat
  • u Standard edice jsou limity na CPU a RAM
  • pozor na dynamickou alokaci zdrojů u VM

Disky

Ideálně mít oddělené disky pro:

  • Windows
  • TempDB
  • data DB
  • log DB

NTFS ideálně 64 KB allocation unit size pro data disky SQL Serveru.

Indexy a klíče

  • Clustered index určuje fyzické uspořádání řádků v tabulce
  • clustered index může být jen jeden
  • nejčastěji bývá na PK
  • nejlepší bývá int jako PK
  • GUID není ideální, protože je dlouhý a špatně se porovnává i vkládá

Hot Pages

Stránky, na které se hodně sahá, třeba kvůli insertům do clustered PK. Při vysoké souběžnosti to může bolet.

Shrink

  • vrací nevyužité místo zpět OS
  • neshrinkovat běžně MDF a NDF
  • nikdy automaticky
  • dává smysl jen výjimečně, třeba po velkém růstu logu nebo rušení souboru

Filestream

Mohu ukládat VARBINARY(MAX) mimo MDF na disk a v databázi mít jen odkaz. Hodí se na velké soubory.

Další poznámky

  • MSSQL je spíš pesimistický přístup – zamykání měněných řádků
  • databázi mohu vytvořit skriptem, attach nebo restore
  • SQL Server umí číst soubory, ale nemám přesouvat DB ručně ve file systemu bez správného postupu
  • co nejmenší transakce, rollback je drahý
  • logy serveru jsou v Management → SQL Server Logs
  • Linked Server – SQL Server se tváří, že má připojený jiný server a může na něj posílat dotazy
  • nevrstvit view na view na view – často velmi nevýkonné
  • Query hint = příkaz optimalizátoru, jak má udělat execution plan
  • fragmentace – do 5 % OK, 5–30 % reorganize, nad 30 % rebuild
  • indexované view – většinou nepoužívat, zpomalují insert/update/delete do base tabulek

SQL CLR

SQL CLR = managed .NET code v SQL Serveru.

  • mohu spouštět C# kód nasazený přímo na SQL Serveru
  • na serveru musí být povolené clr_enabled
  • vytvořím DLL a přes CREATE ASSEMBLY ji nahraji do SQL Serveru
  • pak přes CREATE PROCEDURE nebo funkci napojím .NET metodu

SQL Server Audit a diagnostika

  • audit loguje kdo, kdy a co udělal
  • v SSMS: Security → Audits → New Audit
  • nad tím se dělá Audit Specification, buď serverová, nebo databázová

Když je audit špatně nastavený a SQL kvůli tomu padá, může být potřeba nouzové spuštění v single-user módu a oprava konfigurace.

Extended Events

Management → Extended Events. Zachytí diagnostické události a hodí se při pádech nebo problémech.

Databáze a soubory

Databáze používá stránky o velikosti 8 KB.

Souborová struktura

  • .mdf – primární datový soubor, jeden na DB
  • .ndf – sekundární datové soubory
  • .ldf – transakční log, ideálně na jiném disku

FG = Filegroup. Určuje, do jaké skupiny souborů se ukládají data. U většiny DB se to moc neřeší.

Systémové DB

  • master – seznam databází a konfigurace serveru; bez ní SQL Server neběží
  • msdb – SQL joby, alerty, mail a další „paměť“ serveru
  • model – šablona pro nové databáze
  • tempdb – dočasná data, tabulky, joiny, pracovní prostor SQL Serveru
  • ResourceDB – interní, skrytá systémová DB

Přesun DB

detach databáze, přenesení souborů, pak attach.

DB Properties

  • Auto Close – false
  • Auto Shrink – nezapínat
  • Auto Update Statistics – true
  • Cursor – běžně nenastavovat
  • Legacy Cardinality Estimation – někdy pomůže u starých DB před 2014
  • DOP – dá se přepsat na úrovni DB
  • Parameter Sniffing – první kompilace plánu použije konkrétní parametry a plán pak může být špatný pro jiné hodnoty
  • Query Optimizer Fixes – jestli má SQL Server používat novější opravy optimalizátoru, nebo se chovat postaru kvůli kompatibilitě

Zálohy DB

Základní pojmy

  • RPO – o kolik dat si mohu dovolit přijít
  • RTO – jak dlouho bude trvat obnova
  • zálohovat i systémové DB kromě tempdb
  • nekombinovat nativní SQL backup a backup třetích stran nad stejnou DB bez rozmyslu
  • komprese backupu je většinou super

Typy backupu

  • Full – plná záloha DB
  • Differential – vše změněné od posledního full backupu
  • Log – záloha transakčního logu

Recovery model

  • FULL – log zálohuji sám a mohu obnovovat přesněji
  • SIMPLE – SQL Server si log průběžně čistí sám
  • BULK_LOGGED – výjimečný režim pro speciální operace; nejde obnovit na přesný čas

Další pojmy

  • Backup Set – jedna záloha
  • Media Set – jedno nebo více backup setů na médiu
  • Tail Log Backup – záloha té části logu, která ještě nikdy nebyla zazálohovaná

Obnova DB

RESTORE DATABASE MyDb
FROM DISK = 'E:\SqlBackup\mydb_full.bak'
WITH
  REPLACE,
  NORECOVERY,
  MOVE 'MyDb' TO 'E:\SqlData\MyDb.mdf',
  MOVE 'MyDb_log' TO 'L:\SqlLog\MyDb_log.ldf';

RESTORE LOG MyDb
FROM DISK = 'E:\SqlBackup\mydb_log.trn'
WITH NORECOVERY;

RESTORE DATABASE MyDb WITH RECOVERY;
  • REPLACE – nahradí existující DB
  • NORECOVERY – DB ještě nebude dostupná, čeká na další zálohy
  • RECOVERY – až tady se DB opravdu otevře

Když nejde master

Nejdřív se pokusit SQL Server nastartovat nouzově a obnovit master z backupu. Rebuild systémových DB je až poslední záchrana. 

sqlservr.exe -s DEV -f -m

Nouzové spuštění instance v minimální konfiguraci a single-user režimu. 

setup.exe /ACTION=RebuildDatabase

Poslední záchrana. Znovu vytvoří systémové DB a konfiguraci je pak potřeba obnovit ručně.

SQL funkce a konstrukce

CTE

Common Table Expression – pojmenovaný select.

WITH Name AS (
  SELECT *
  FROM dbo.TableName
)
SELECT *
FROM Name;

Window funkce

Pro každý řádek spočítám hodnotu z okolních řádků podle definice okna. 

SUM(Value) OVER (
  ORDER BY Id
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)

APPLY

  • CROSS APPLY – podobné jako INNER JOIN, pravá strana se vyhodnocuje pro každý řádek zleva
  • OUTER APPLY – podobné jako LEFT JOIN

Indexy

  • Unique – hodnoty musí být unikátní
  • Clustered – jeden na tabulku, fyzické seřazení dat, ideálně úzký, statický, rostoucí klíč
  • Nonclustered – může jich být víc, často na časté dotazy
  • Composite – index přes více sloupců
  • INCLUDE – přidá další sloupce do nonclustered indexu, aby nebyl potřeba key lookup 
CREATE INDEX IX_Users_Email_Name
ON dbo.Users(Email, Name)
INCLUDE (CreatedAt, Status);

Pořadí sloupců v composite indexu je důležité.

Vyhledání textu ve všech tabulkách

DECLARE @hledana NVARCHAR(100) = 'Red';
DECLARE @sql NVARCHAR(MAX);

DECLARE crs CURSOR FAST_FORWARD FOR
WITH columns_metadata AS
(
    SELECT
        CONCAT(OBJECT_SCHEMA_NAME(t.object_id), '.', t.name) AS full_table_name,
        STRING_AGG(
            CONCAT('[', c.name, '] LIKE ''%', @hledana, '%'''),
            ' OR '
        ) AS predicate
    FROM sys.tables t
    JOIN sys.columns c ON t.object_id = c.object_id
    WHERE c.system_type_id IN (231, 35, 99, 167, 175, 239)
    GROUP BY CONCAT(OBJECT_SCHEMA_NAME(t.object_id), '.', t.name)
)
SELECT
    'IF EXISTS(SELECT * FROM ' + full_table_name +
    ' WHERE ' + predicate +
    ') PRINT ''' + full_table_name + ''''
FROM columns_metadata;

OPEN crs;
FETCH NEXT FROM crs INTO @sql;

WHILE @@FETCH_STATUS = 0
BEGIN
    EXEC(@sql);
    FETCH NEXT FROM crs INTO @sql;
END

CLOSE crs;
DEALLOCATE crs;

Detailnější skript na fragmentaci

SELECT
    o.name AS TableName,
    i.name AS IndexName,
    ips.index_type_desc AS IndexType,
    ips.page_count AS PageCount,
    ROUND(ips.avg_fragmentation_in_percent, 2) AS LogicalFragPercent,
    ROUND(100 - ips.avg_page_space_used_in_percent, 2) AS InternalFragPercent,
    CAST(
        ROUND(
            ips.page_count * (ips.avg_page_space_used_in_percent / 100.0),
            0
        ) AS int
    ) AS EstimatedPageCountAfterRebuild
FROM sys.dm_db_index_physical_stats
(
    DB_ID(),
    NULL,
    NULL,
    NULL,
    'DETAILED'
) ips
JOIN sys.objects o
    ON ips.object_id = o.object_id
JOIN sys.indexes i
    ON ips.object_id = i.object_id
   AND ips.index_id = i.index_id
WHERE
    o.type = 'U'
    AND ips.page_count > 1000
ORDER BY InternalFragPercent DESC;
