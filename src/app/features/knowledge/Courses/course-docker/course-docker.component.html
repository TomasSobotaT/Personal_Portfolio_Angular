Data a volumes

Defaultně se data ukládají do kontejneru. Když kontejner smažu, o ta data přijdu. Proto řeším volumes nebo bind mounty. :contentReference[oaicite:6]{index=6}

Volumes

  • soubory mimo samotný kontejner
  • nesmažou se jen tím, že zastavím nebo znovu vytvořím kontejner
  • jsou managované Dockerem

Anonymous Volumes

docker run -v /app/data my-image

Docker vytvoří anonymní volume. Typicky žije, dokud existuje nebo je navázaný na kontejner a Docker ho spravuje. :contentReference[oaicite:7]{index=7}

Named Volumes

docker run -v data:/app/data my-image

Named volume má svoje jméno a přetrvá i po smazání konkrétního kontejneru, dokud ho nesmažu zvlášť. :contentReference[oaicite:8]{index=8}

Bind Mounts

docker run -v /path/to/code:/app/code my-image
  • moje data, mnou managovaná
  • připojí adresář z hosta do běžícího kontejneru
  • kontejner čte a zapisuje přímo do těch dat na hostiteli
  • nemusím při změně kódu znovu buildit image

To je super hlavně při vývoji. Bind mounty jsou přímo svázané se strukturou souborů hostitele. :contentReference[oaicite:9]{index=9}

Read-only bind mount

docker run -v /path/to/code:/app/code:ro my-image

Připojení jen pro čtení. Docker bind mount podporuje režim readonly / ro. :contentReference[oaicite:10]{index=10}

ARG a ENV

ENV

docker run -e PORT=8000 my-image

Proměnné prostředí při běhu kontejneru.

ARG

ARG DEFAULT_PORT=80

Argument použitelný v Dockerfile při build procesu.

docker build --build-arg DEFAULT_PORT=8000 -t my-image .

ARG je build-time proměnná, ENV bývá runtime proměnná v image nebo kontejneru. :contentReference[oaicite:11]{index=11}

Networking

Web

Kontejner může normálně komunikovat se sítí a webem podle toho, jak je spuštěný a namapovaný.

Container -> localhost app

Uvnitř kontejneru není localhost tvůj počítač, ale sám kontejner.

Proto se pro přístup na hostitele často používá host.docker.internal.

Container -> Container

  • mohu si vytvořit vlastní Docker síť
  • kontejnery v jedné síti spolu komunikují přes jméno služby nebo kontejneru 
docker network create my-network
docker run --network my-network --name mongodb mongo
docker run --network my-network my-backend

V Compose se tohle řeší ještě pohodlněji přes názvy služeb. Compose umí definovat služby, sítě i volumes v jednom souboru. :contentReference[oaicite:12]{index=12}

FE v kontejneru často volá BE jinak podle toho, kde opravdu běží klient. Když FE běží v browseru, není to totéž jako komunikace kontejner-kontejner.

Docker Compose

Docker Compose v podstatě nahrazuje víc docker run a docker build příkazů jedním YAML souborem. Compose definuje služby, sítě a volumes. :contentReference[oaicite:13]{index=13}

Spuštění

docker compose up
docker compose up -d
docker compose up --build
docker compose build

Zastavení

docker compose down
docker compose down -v

docker compose up buildí, vytváří a startuje služby podle konfigurace, pokud už neběží. :contentReference[oaicite:14]{index=14}

V YAML mohu odkazovat na image, nebo na Dockerfile přes build, a zároveň si doplnit porty, volumes, environment proměnné a závislosti mezi službami. :contentReference[oaicite:15]{index=15}

Multistage builds

Stejně jako u .NET: nejdřív build stage, potom runtime stage. Dockerfile reference popisuje vícestupňové buildy přes víc FROM instrukcí. :contentReference[oaicite:16]{index=16}

Dockerfile

Dockerfile zároveň vytváří vrstvy image. Každá vrstva je cacheovatelná, takže pořadí instrukcí je důležité. Když změním něco nahoře, přebuildí se i vrstvy pod tím. Docker build cache a Dockerfile reference to popisují přímo. :contentReference[oaicite:17]{index=17}

Základní instrukce

FROM node

Z jakého base image se nový image staví.

WORKDIR /app

Nastaví pracovní složku v kontejneru.

COPY . .

Zkopíruje obsah build contextu do image.

ARG DEFAULT_PORT=80

Build argument.

ENV PORT=$DEFAULT_PORT

Proměnná prostředí.

EXPOSE 80

Jen deklarace portu, ne reálné publikování ven. Porty se reálně mapují při docker run -p. :contentReference[oaicite:18]{index=18} 

VOLUME ["/app/feedback"]

Mount point pro volume.

CMD ["node", "server.js"]

Výchozí příkaz při startu kontejneru.

ENTRYPOINT ["node", "server.js"]

Entry point, který se spouští vždy jako základ startu kontejneru.

.NET Dockerfile

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]

Obecně k Dockeru

  • mohu mít i Windows image s Windows jádrem, ale jsou větší a potřebují odpovídající host prostředí
  • default je většinou Linux world
  • image jsou read-only, běhový zápis jde do writable vrstvy kontejneru
  • do kontejneru mohu za běhu kopírovat věci
  • pořadí volumes a bind mountů může přepisovat obsah z předchozích vrstev nebo mountů
  • .dockerignore funguje podobně jako .gitignore
  • name:tag = název image a konkrétní tag

Docker Compose YAML

services:
  mongodb:
    image: "mongo"
    volumes:
      - data:/data/db
    environment:
      MONGO_INITDB_ROOT_USERNAME: max
      MONGO_INITDB_ROOT_PASSWORD: secret

  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    ports:
      - "80:80"
    volumes:
      - logs:/app/logs
      - ./backend:/app
      - /app/node_modules
    environment:
      MONGODB_USERNAME: max
      MONGODB_PASSWORD: secret
    depends_on:
      - mongodb

  frontend:
    build: ./frontend
    ports:
      - "3000:3000"
    volumes:
      - ./frontend/src:/app/src
    stdin_open: true
    tty: true
    depends_on:
      - backend

volumes:
  data:
  logs:

Compose specification dnes používá sekce jako services a top-level volumes. Named volumes se definují nahoře a pak se používají ve službách. :contentReference[oaicite:19]{index=19}

Kubernetes

Kubernetes je v podstatě orchestrátor kontejnerů, něco jako „Docker Compose pro víc VM / serverů“, ale mnohem silnější. Řeší automatizaci nasazení, škálování a správu kontejnerových workloadů. :contentReference[oaicite:20]{index=20}

  • nahrazuje vypadlé kontejnery
  • škáluje aplikace
  • distribuuje požadavky

Cluster

  • Control Plane – řídicí vrstva clusteru
  • Worker Nodes – stroje, které skutečně spouští workload

Pod

  • nejmenší jednotka, se kterou Kubernetes pracuje
  • jeden nebo více kontejnerů běžících společně
  • kontejnery v Podu sdílí síťový namespace, takže spolu mluví přes localhost
  • Pod má vlastní IP v clusteru, ale ta není stabilní navždy
  • Pod sám o sobě není perzistentní objekt pro dlouhodobý přístup zvenku

Oficiální dokumentace Pod popisuje právě jako nejmenší nasaditelnou jednotku a Service dokumentace řeší stabilní přístup přes Service IP a load balancing. :contentReference[oaicite:21]{index=21}

Další části

  • kubelet – agent na worker nodu
  • API Server
  • Scheduler
  • Controller Manager

Nástroje

  • kubectl – oficiální CLI pro ovládání clusteru. :contentReference[oaicite:22]{index=22}
  • minikube – lokální cluster pro vývoj.

Kubernetes objekty

Kubernetes pracuje s objekty jako Pods, Deployments, Services a Volumes. Ty objekty mohu vytvářet imperativně nebo deklarativně přes YAML. Service a Deployment jsou standardní objekty popsané v oficiálních docs. :contentReference[oaicite:23]{index=23}

Deployment

  • většinou neposílám přímo Pod, ale definici Deploymentu
  • Deployment říká, co a kolikrát nasadit
  • mohu dělat rollout, rollback, změny konfigurace a škálování

Service

  • stabilní vstupní bod k Podům
  • řeší IP, load balancing a service discovery

Kubernetes volumes

Docker volumes a Kubernetes volumes nejsou totéž. V Kubernetes řeším storage pro Pody a často i přístup napříč nody podle storage typu a access modes.

Persistent volume access modes

  • ReadWriteOnce (RWO) – čtení a zápis na jednom nodu
  • ReadOnlyMany (ROX) – jen čtení na více nodech
  • ReadWriteMany (RWX) – čtení a zápis na více nodech
  • ReadWriteOncePod (RWOP) – čtení a zápis pro jeden Pod

Deklarativní přístup

Místo přímých příkazů je lepší používat YAML soubory a nasazovat je deklarativně přes kubectl apply. 

kubectl apply -f deployment.yaml

Deployment YAML

apiVersion: apps/v1
kind: Deployment

metadata:
  name: second-app-deployment

spec:
  replicas: 1
  selector:
    matchLabels:
      app: second-app
      tier: backend

  template:
    metadata:
      labels:
        app: second-app
        tier: backend

    spec:
      containers:
        - name: second-node
          image: academind/kub-first-app:2

Service YAML

apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  selector:
    app: second-app
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
  type: LoadBalancer

Service v Kubernetes vybírá cílové Pody typicky přes label selector. To je základní princip, jak Service ví, kam má provoz směrovat. :contentReference[oaicite:26]{index=26}

Hints

  • Docker = image + container + volumes + networking
  • Compose = více kontejnerů přes jeden YAML
  • Kubernetes = orchestrátor nad kontejnery
  • Pod není totéž co container
  • Service dává stabilní přístupový bod k Podům
  • Deployment je běžný způsob, jak říct kolik Podů chci a jak mají běžet
  • Pořadí instrukcí v Dockerfile hodně ovlivňuje cache a rychlost buildů
  • Na dev a prod často používám jiný Dockerfile nebo jiný build flow
